# VERIFY

执行前必须确认：

1. 待办分页已成功取完，编号来自当前快照；业务单号不能替代 `requestId`。
2. 查询详情前目标 requestId 在当前待办校验中有效；`STALE_REQUEST`、`TODO_ID_UNRESOLVED` 或待办检查失败即停止。
3. 人工写操作的对象、动作和用户授权明确；拒绝有原因和有效退回节点，转发有明确目标。
4. 自动审批逐项先有成功摘要/详情，并且详情返回唯一的、启用的、允许自动执行的匹配规则；按 SOUL 固定分类重算分数（`normal=100`、`sensitive=50`），只允许 `matched_score > 50` 且无 `UNKNOWN`、冲突或风险阻断的规则进入自动审批；历史偏好不能作为自动执行条件。
5. 规则写入前，预览或模拟已完成，且每个条件的 `category` 只能是 SOUL 定义的 `normal`/`sensitive`，权重必须由固定映射重算，模型和用户都不能改分类定义或阈值语义。规则摘要、`preview_token` 和 `scope_key` 与确认内容一致；删除、停用也有明确确认。
6. 定时任务的频率/时刻、时区、到点动作明确；若涉及自动审批，已存在对应启用规则。

执行后必须确认：

1. OA 返回业务成功，而不只是 HTTP 成功；写操作或自动审批后刷新待办。
2. 权限、过期、ID 解析、业务失败和平台调度失败按真实类别反馈。
3. 批量结果逐项记录；一个对象失败不会把该对象继续写入，也不会误报其他对象成功。
4. 详情失败时回复只含刷新、跳过或结束，不含批准、拒绝、转发或基于旧摘要的审批建议。
5. 未收到平台成功回执时，不得声称定时任务已创建。
